# 从旧记录与完整新版 RTL 自动推导局部替换

```bash
python3 -m incremental auto \
  --base-run runs/old-run \
  --new-source path/to/new.v \
  --out runs/automatic-edit
```

输入是旧综合运行目录和完整新版 RTL；多个源文件重复 `--new-source`。不需要提供修改行号、实例、局部代码、契约或绑定。`--out` 必须是新目录。工具链路径可通过 `--yosys`、`--native-yosys` 指定。

旧记录必须包含校验通过的 `frontend.il`、最终网表、来源及 ABC 证据。源码文件可以已被修改或删除。顶层名、顶层参数、宏、include 目录和是否 flatten 继承旧 manifest；新版需能在这些编译条件下展开，新增 include 文件仍需可访问。本轮不提供编译配置迁移，要求顶层端口名、方向、位宽及位序保持不变。

## 推导过程

1. **读取旧表示。** 重放、校验旧记录，读取当时保存的 `proc` 前 `frontend.il`，不重新读入或综合旧源码。
2. **展开完整新版。** 用原生前端及 `hierarchy` 展开新版，保留完整过程体、端口、参数和实例关系。另运行 `proc; check` 检查组合逻辑范围、计算端口依赖；这里没有运行 `synth`、`techmap` 或 ABC。保存全部源文件/include 的哈希。
3. **自动比较。** 按实际实例路径匹配新旧模块，用规范化 `proc` 前表示比较模块本体；忽略源码坐标等非功能元数据，统一自动生成标识符。模块定义重命名本身不算修改，连接和过程内容变化会被发现。共用定义发生变化时会发现所有受影响实例，父模块端口接线或实例结构变化则选择父模块。
4. **生成旧区域契约。** 根据变化实例在旧表示中的模块源码范围，查询旧来源，纳入子实例并合并契约。仍要求 `verified_old_region`；候选来源不会因为自动选区或全输出验证而升级。
5. **提取新版局部功能及绑定。** 从新版前端表示复制选中模块和所需子模块，生成带契约端口的包装模块。保留完整过程体，不按文本行剪裁 `always`。输入输出通过已验证的旧实例视图、端口绑定或实际 flatten 复制关系连接；没有这些证据时不猜测同名关系。
6. **处理新增依赖。** 新版使用、旧契约尚未包含的输入，必须是旧网表上有唯一外部驱动的实际信号。生成 `extend_inputs` 契约并重新验证全部旧输出；其来源成员不变。只有新版粗粒度依赖分析证明无输出使用的输入位才允许接 0；该判定还要通过最终全输出验证。
7. **必要时扩大区域。** 当局部接口变化、输出身份不唯一、边界信号不可用或旧区域未证明时，尝试父实例并重新计算契约和绑定。顶层仍不能满足条件就报告 `blocked`，保留具体尝试和原因，不发布结果。
8. **局部综合、拼接、验收。** 只综合提取的 `patch.il`，验证所有边界输出、外部消费者、单驱动、无环及未选门不变。候选生成后，才完整综合冻结的新版前端表示作为参考，验证全部顶层输出和交付 Verilog 重读等价。最后复核旧归档及新版输入哈希，发布网表。

规范化差分是结构比较，不是功能等价证明。条件等价改写可以被判为修改，独立语句重排也可能产生保守扩区；最终全输出 SAT 验收始终保留。若没有结构变化，则直接复用全部旧门，仍验证完整新版与输出 Verilog。

## 粒度与限制

当前粒度是**最先发生本体变化的模块实例集合，必要时向父实例扩大**。模块本体未变时才递归比较子实例；不声称最小语句区域。单模块 RTL 的修改可能选择整个顶层，此时会如实报告复用门数，不能称为获得了局部复用收益。

支持范围继承组合来源前端：普通组合层次、连续赋值及已支持的组合过程；时序、锁存、memory、generate、循环、函数/任务仍拒绝。参数派生模块保留真实 `$paramod` 身份。保留层次或显式 flatten 的旧记录都可输入，但展平后的 ABC 证据缺口仍可能阻塞；交付网表是展平的通用门网表。

当前不自动拆分同一旧信号的不同消费者，不保证能处理新直连/常量变门、端口身份消失、任意模块接口变化或任意共享改写。扩大到顶层也不能消除候选来源或连接义务。部分情况最终报告验证失败，均不发布网表。失败是当前策略或证据的限制，不说明这项 RTL 编辑无法通过其他方式实现。

验证只适用于本次完整新版及实际绑定，继续保留旧契约的 `safe_for_incremental_reuse=false` 和来源缺口声明。没有生成替换后设计的完整连续来源日志。

## 产物与验收

| 路径 | 内容 |
| --- | --- |
| `difference.json` | 实例、旧/新模块及源码范围、规范表示差异和指纹 |
| `region.contract.json` | 自动选择、并集或增加输入后的可重放契约 |
| `patch.il` / `patch.v` | 只包含局部功能及包装；Verilog 是便于检查的转换结果 |
| `bindings.json` | 全部边界输入输出的自动连接 |
| `patch-specification.json` | 实际端点证据、新增输入、被证明未使用的输入、选中模块 |
| `work/new.frontend.il` / `new.coarse.json` | 完整新版展开结果及组合检查表示 |
| `replacement/` | 局部综合、拼接、独立边界检查、完整新版参考及全部验证脚本/日志 |
| `incremental.v` / `incremental.json` | 全部检查通过后才交付的网表 |
| `report.json` | 状态、扩区尝试、门数、哈希、逐阶段耗时及失败原因 |

`status=unchanged` 时不生成 patch，保存复用和等价验证结果。`blocked` 或 `failed` 的 `auto` 命令非零退出。`incremental_candidate_ready_seconds` 包含旧记录重放、新版前端和组合检查、差分、契约生成验证、绑定、局部综合与拼接；完整新版参考综合和验收单独记录，没有时间加速承诺。

用 ANUBIS 复现自动模式：

```bash
python3 -m incremental anubis --automatic \
  --cases compare_local9 --mode retained --out runs/automatic-anubis
```

基准准备器只负责生成完整版本并综合旧版，随后仅把旧运行目录和新版文件交给自动算法；不提供预设目标实例、源码行号或局部规范。`compare_local9` 自动发现 `benchmark/u_target`，替换 115 个门、复用 116 个门，通过全部输出验证。完整六用例 × 两种模式实测为 4 项成功、2 项预期锁存拒绝、6 项证据不足阻塞；不能把这些阻塞计为支持成功。

`incremental/tests/test_automatic.py` 还覆盖格式/模块名变化时全部复用、共用定义修改自动选择两个实例、参数派生、新增输入依赖、旧源码删除、归档篡改、候选不得升级、契约输入扩展导出及合并内部化。测试 RTL 来自 ANUBIS 及明确标注的参数/接线包装变体。完整回归会保存 `automatic/` 下的脚本与产物，便于复核。
