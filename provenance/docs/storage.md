# 来源记录与查询索引：SQLite / gzip

首次插桩综合保存原始证据，完整验证后默认生成 `verified-index.sqlite3`，也可选择去重后的 `verified-index.json.gz`。新版 RTL 到来后，按修改种子查询来源和转换边，重新计算本次所需区域及边界。索引是可重建的查询副本，不替代原始证据，也不改变来源精度或替换条件。

## 后端选择

```bash
# 默认值为 sqlite，省略选项时行为不变
python3 -m yosys_flow run --source provenance/examples/comb.v --top demo \
  --out runs/storage-sqlite --index-backend sqlite
# 整包加载的去重 gzip
python3 -m yosys_flow run --source provenance/examples/comb.v --top demo \
  --out runs/storage-gzip --index-backend gzip
python3 -m yosys_flow query runs/storage-gzip --source provenance/examples/comb.v --line 4
```

每次建档只生成选中的后端，`configuration.index_backend` 记录选择，`verified_index` 绑定具体文件。后续 `query`、`extract`、契约与 `incremental auto` 按 manifest 自动识别，不需要重复传参；原始 JSONL 始终保留。此选项用于新建归档，不会转换或覆盖已有运行目录，也没有增加常驻服务。后端选择不改变 Yosys 的综合流程。

`index_store.py` 共用去重行生成器、共享字段解码、查询视图及缓存规则。SQLite 将同一组行写入数据库并建立磁盘索引；gzip schema 2 把这些行直接写入压缩 JSON，加载时建立内存映射、位置/标签和正反向邻接索引。gzip 不先创建 SQLite，也不展开重复的大数组；旧 gzip schema 1 的整包 trace 读取兼容仍保留。两边共用来源路径、门组闭合、全部输出验证与替换条件，不能因后端变化提高关联精度。

两种新后端都在完整验证后原子发布，并绑定原始产物、版本和本机认证签名。现有索引损坏时拒绝；索引缺失、格式或实现版本变化、缺少本机密钥时按既有规则回退原始重放。gzip 与 SQLite 采用不同的签名域，不能把一种后端的签名用于另一种。

## ABC 检查点与差量

ABC 内部 schema 5 保留既有事件序号和网络快照编号，对 AIG/GIA 历史网络使用两种编码：

- `checkpoint` 保存完整节点集和输入、输出 literal。
- `delta` 引用 `base_snapshot`，保存新增/修改节点、`deleted_nodes` 及当前端口。节点内容包括操作和带极性的扇入；删除后仍被引用的节点会被拒绝。

只有同一命令、同一表示、同一 manager 的连续历史观察可以使用差量。命令/manager 切换、显式网络检查点及每 128 次历史观察重新开始完整检查点。`network_epoch` 是编码作用域；它不能证明跨快照节点身份，实际来源仍由复制、合并、映射等记录和功能验证建立。原有对象的版本、退休、复制映射和 literal 极性均保留。

重放器按序还原每个快照，检查基础快照是否为同 epoch 的最新状态、删除是否合法、端口与扇入是否完整；原先的事件计数、复制表、关系及函数校验继续执行。旧 schema 1–4 仍可读。测试专用环境变量 `YOSYS_FLOW_ABC_FULL_SNAPSHOTS=1` 可强制写完整检查点，用于比较两种编码的逐快照节点、端口和最终网表。

上述差量编码只压缩重复 AIG/GIA 历史网络。NTK、BLIF 仍保留原有记录方式；Yosys 原生日志另采用下述共享数组编码。记录器仍扫描网络以发现变化，重放也仍要验证恢复出的状态。因此文件减少不等于相同比例的计算时间减少，schema 5 也不表示已经补齐 `dc2/dch` 的全部因果历史。

## 原生来源集合与区域关系

原生 JSONL v2 通过 `shared_native_arrays_v1` feature 声明共享数组。长度至少 32 的来源 ID 和转换输入集合先写一条 `shared_array` 定义，后续事件以 `{"$native_array": id}` 引用；短数组仍直接内联。定义带独立的事件序号和当前 step ID，必须先于引用，且区分 `origins` 与 `inputs`。错用类型、未知引用、重复定义和未知来源均拒绝。记录器内的 cell/connection 及当前记录作用域共享不可变来源集合，贡献发生变化时才创建新集合。已登记集合的身份和序列化引用可直接复用，避免逐 cell 优化时反复复制、逐项比较完整来源集合。

读取端保留原始记录，解码的来源数组由对象版本和事件共享。ABC 提取成员及来源并集在 `abc_region` 验证一次，每个输出继续核对它与该区域的成员、来源和候选精度完全一致。查询图将相同的 N 个输入到 M 个输出关系表示为 `输入 → 区域节点 → 输出`；细化后的相同大成员集合也可共享节点。节点不声明新的因果证据，严格保留来源可达性、事件先后和原来的精度。不同成员集合不会因为属于同次调用而合并。

测试专用变量 `YOSYS_FLOW_NATIVE_FULL_ARRAYS=1` 可恢复内联编码，供逐项比较原始来源、最终网表和查询选择。没有该 feature 的旧 v2 日志仍可重放；旧读取器不会静默接受新编码。

## SQLite 表与按需读取

数据库在离线验证后用一个事务构建，完整性检查通过后原子发布。可检索键单独存储，载荷逐条压缩并按 SHA-256 去重。转换边的端点通过 `refs` 表归一化为整数键，事件号独立存列，剩余公共字段共享模板；不再为每条边另存整份 JSON。模板和其他载荷也以整数键引用，避免重复保存长摘要：

| 表/索引 | 用途 |
| --- | --- |
| `positions` / `source_location` | 文件及行范围查询源码身份，随后保留原有列和实例筛选 |
| `items` | 按字段与键访问对象版本、来源、连接及各类证据 |
| `edges` / `edge_from` / `edge_to` | 正反向来源关系与按原始顺序的路径检查 |
| `refs` | 源码 ID、对象版本等带类型身份与整数 SQL 键之间的映射 |
| `lookup.sources_to_final`、`lookup.sources_to_assignments` | 源码身份到最终对象及连接 |
| `lookup.drivers`、`lookup.consumers`、`lookup.aliases` | 信号的驱动、使用者和别名 |
| `tags` | 按对象、事件序号、调用及相关来源定位证据行 |
| `joint_groups` / `joint_members` | 离线追踪得到的门组最终成员、缺失成员，在线只读取触及的组 |
| `documents` | 按内容摘要去重的压缩载荷，引用使用整数主键 |
| `document_fields` | 大型来源/成员数组单独保存，各对象版本共享引用并按需还原 |

SQLite schema 2 将重复的大数组从行载荷中分离，避免对每个对象版本重新序列化、压缩和保存。同一查询中的载荷缓存仍有界；共享字段必须引用已存储的数组文档，不能递归引用自身。schema 1 索引失效时仍从原始证据重放。

表中的 `lookup.*` 是 `items.field` 值，不是另建的 SQL 表。对象反查读取对象版本中的来源 ID，再按 ID 取源码行；无需全量恢复来源表。

查询通过只读 SQLite 连接和有界载荷缓存访问这些表，不先解压整个 trace。门组闭合的成员关系在首次建档时计算，在线沿成员索引扩展触及的组，避免每次重新遍历全部 ABC 证明载荷。图遍历保留原有事件先后约束，不能把任意可达路径误当成符合日志顺序的来源链。单门只需确认路径存在时允许找到第一条后停止；契约读取成员信息时也不再为每个门生成随后丢弃的完整反查报告。自动流程的紧凑选区只返回成员与来源 ID，避免先展开完整源码详情再丢弃。目标较多时一次检查它们从所选来源出发的有序路径，不逐门重复扫描共享祖先；少量目标仍使用提前停止的反向查找。完整证据导出仍获取所需全部支持关系。

最终电气设计和少量运行上下文仍一次读入，部分显式完整诊断/导出会请求全部相关记录。每次加载仍完整计算原始产物和数据库的哈希；哈希读取采用流式实现。这些成本不会因数据库按需查询而消失。

## 认证、兼容与复核

manifest 将数据库绑定到同次运行的原始产物、运行配置及验证实现。构建前后核对原始证据；描述符通过本机密钥认证，密钥不进入归档或 Git。加载先检查文件哈希、绑定和认证，再打开数据库；修改数据库后仅重新计算普通 SHA-256 不能绕过认证。

索引缺失、实现/格式不匹配或缺少本机认证密钥时，读取原始记录重新验证，不自动修改旧归档。现有索引损坏或认证失败会拒绝；需要明确使用原始重放进行诊断。旧 gzip schema 1 仍有读取路径，新建归档默认写 SQLite，也可显式选择去重 gzip schema 2。现有旧证据不必重新综合即可重放，但新差量编码的体积收益只适用于重新记录的运行。共用存储层的实现变更会使先前索引指纹失效，旧归档此时走完整重放，不会静默改写索引。

```bash
# 建档，索引在完整验证后生成
python3 -m yosys_flow run --source provenance/examples/comb.v \
  --top demo --out runs/sqlite-demo

# 默认使用有效索引；索引失效则重放原始证据
python3 -m yosys_flow query runs/sqlite-demo \
  --source provenance/examples/comb.v --line 2

# 强制完整重放，独立于索引命中
python3 -m yosys_flow validate runs/sqlite-demo
```

## SQLite 与去重 gzip 的同数据对比（2026-10-26）

本轮先提交检查点 `f590528`，随后只增加临时实验代码，没有改动生产后端。结论是：**去重 gzip 的构建、文件体积和加载后重复查询更有优势；SQLite 的首次恢复与内存占用更有优势。现有数据不支持“SQLite 在所有阶段都更快”。**

### 固定数据与协议

使用 `runs/storage-optimization-release/{adder,bar}/baseline/base-run/` 两份已经通过验证的记录；`arbiter` 尚无验证完成的归档，因此不混入本次对比。读取原始归档时执行现有完整性与认证检查，然后只抽取一次共同的去重表示。它保留所有文档 ID、共享数组引用、转换边端点、事件顺序、查询映射和门组数据，没有减少候选证据。

共同表示是现有 schema 2 的十张逻辑表：`documents`、`document_fields`、`fields`、`items`、`refs`、`edges`、`positions`、`tags`、`joint_groups`、`joint_members`。文档保留原 JSON 载荷，公共字段继续通过 ID 引用。两边都从这一份数据生成文件：

- SQLite：按现有表结构和索引重新建库，文档逐条 zlib level 1 压缩，单事务提交，采用默认同步设置及 DELETE journal。
- gzip：将相同逻辑表保存为一个 JSON 包，文档载荷为 JSON 字符串，整体 gzip level 1 压缩；加载时建立内存字典、源码位置、标签及正反向邻接索引。它不是旧版未去重的整份 trace 序列化，也不是 gzip 压缩 SQLite 数据库。
- 两边复用同一套字段解码和生产查询/契约算法，解码文档缓存都限制为 512 项、8 MiB 原始载荷。该上限不包含 gzip 整包读取后常驻的表与内存索引，也不等于进程总内存上限。

每个电路、每个后端各三次：共 12 次构建、12 次加载与查询进程。固定随机种子 `20261026` 打乱后端/电路/重复顺序，串行运行，绑定 CPU 0；每次构建及查询均为独立进程。CPU 为 Intel Xeon Gold 5220R 2.20 GHz，Python 3.10.12，SQLite 3.37.2。

“构建”从已加载的共同去重表示开始，包含后端编码、压缩、写入、SQL 物理索引及提交；不含原始记录重放、共同归一化/去重、公共证据验证及签名。构建后的文件哈希、完整逻辑表一致性检查在计时之外，两边都执行。因此本节的 1.97 s 等数值不能直接替代前面生产流程中包含更多工作的 9.25 s 建档阶段。

“首次加载”指新进程打开后端并恢复相同的必要运行上下文。每次先校验相同原始产物，再校验本次后端文件，校验分别计时；这会预热文件缓存，**不是冷盘测试**。没有清理主机 page cache，也没有计入重新综合。

每个查询进程按 local、shared、module 顺序完成三个真实的 `source_cells` 紧凑区域计划：源码选择、有序来源路径、门组闭合、边界与全部输出函数验证、共享义务和证据引用都执行。每个任务使用新契约上下文，后端及其解码缓存持续存在；完整选区不包含新旧 RTL 差分、patch 提取或综合拼接。

之后执行五轮重复查询；每轮包含上述三个源码查询，调用真实 `query_loaded(..., compact=True)`，不使用最终查询结果缓存。重复查询不重新生成完整契约。每进程先取五轮中位数，再在三次进程结果中取中位数；下文“每批”始终指三次查询。

### 对项目的选择

本轮证实，去重和共享结构的收益并不专属于 SQLite：采用同样结构的 gzip 在这两个案例中写得更快、文件更小，加载后在内存中进行大范围或重复查询也更快。SQLite 将物理索引建设放在首次建档，在线恢复很轻，且无需在每个新进程中恢复全部表。

对于当前“每次新 RTL 启动一个进程，优先找小区域”的 CLI，继续保留 SQLite 默认后端有依据，尤其是首次响应和内存；对于数据能放入内存、长驻进程反复查询的场景，去重 gzip 值得考虑。不能用这两个案例推断所有规模的胜负，也不能将本节后端构建时间冒充全量建档时间。当前差分和函数证明瓶颈仍需独立优化，本轮没有切换生产后端。
