# 来源记录与查询索引：SQLite / gzip

## 捕获端的缓存与记录压缩（2026-11-16）

本轮优化发生在插桩 Yosys/ABC 写出原始证据时，与 SQLite/gzip 索引后端无关。保持完整默认 `synth`、实际来源事件、独立设计检查和最终网表语义；没有启动完整 hyp 重测。问题定位见 [hyp 诊断](../../incremental/hyp-comparison.md#单独捕获与普通综合的开销定位2026-11-16)。

**共享输入缓存。** 同一活动输入列表只进行一次内容去重，后续 cell/connection 直接复用编码后的数组引用。进入和退出 `CellScope/RegionScope`、清空/重建列表，以及 `contribute()` 更新对象版本时都使活动缓存失效；恢复旧作用域时重新解析一次原集合 ID。没有按可变 vector 地址缓存，也不在每次引用时重新扫描列表计算哈希。`run_end.recorder_stats.input_content_lookups/input_cache_hits` 可检查是否重新出现逐门查找大集合的退化。

**原生检查点。** `native_checkpoint_deltas_v1` 在 JSONL v2 中声明无损的检查点编码：首个、每隔 32 个检查点及最终 `run_end` 保存完整 cell/connection 状态清单，其间保存相对上一检查点的 cell 增删和连接版本变化。对象仍按实际设计逐个观察，未知 pass 的扫描兜底保持不变；压缩清单不等于省略状态检查。读取端独立恢复检查点，并与事件重放得到的所有活跃对象和连接版本核对，拒绝缺失/过期基点、重复增删、错误版本、数量不符及以差分代替最终完整检查点。没有新特性标记的旧全量检查点继续支持。

**ABC 接口。** `shared_snapshot_interfaces_v1` 在内部 schema 5 中声明接口继承。AIG 增量快照只有在实际 PI/PO ID 与顺序均相同时才引用紧邻的前一快照；输入/输出改变时显式重写接口。新 manager、command、epoch 或完整检查点会重置缓存。读取端先检查网络身份和即时基点，再继承不可变接口，并照常检查节点创建、删除、极性及 fanin/输出存在性；原始记录不会被解码过程修改。缺失的引用、跨网络引用、冲突的显式接口均拒绝。

**状态编码。** cell 缓存保存不可变 JSON 状态，采用值比较后只在事件写出时序列化一次，避免先 dump 状态用于比较、再 dump 整条事件。此处以部分额外内存换取较少的字符串构造；不能假设所有电路的峰值内存都会下降。

可用 `YOSYS_FLOW_NATIVE_FULL_CHECKPOINTS=1` 与 `YOSYS_FLOW_ABC_FULL_INTERFACES=1` 恢复展开记录作独立对照；平时取消设置即可。`YOSYS_FLOW_NATIVE_AUDIT=1` 仍同时启用完整状态构造和全部检查点审计。与优化前工具相比，这些诊断模式也保留共享输入缓存修复。

### 分阶段计时

默认不启动细计时。运行插桩 Yosys 时设置 `YOSYS_FLOW_CAPTURE_PROFILE=1`，可得到：

* 原生日志 `step_end.elapsed_seconds_inclusive`：各 pass 的墙钟时间，包含嵌套 pass。
* `run_end.capture_profile.timings`：状态构造、JSON 编码、流写入/中间 flush、检查点及 ABC 回填的累计耗时和次数。检查点、ABC 回填是包含子步骤的时间，不得与编码/写入时间简单相加。最终 `run_end` 自身的写入及最终 close 不在这些累计项中；最终检查点不在检查点累计项中。
* ABC 日志 `command_end.cpu_seconds_inclusive`：各条 ABC 命令及其钩子的进程 CPU 时间。它与原生 pass 的墙钟时间口径不同，不能混作不重叠的分段总和。

建议同时给 Yosys 加 `-t`，保留人能直接阅读的日志阶段时间戳，并继续用 `/usr/bin/time -v` 测完整捕获墙钟和 RSS。该计时选项只添加诊断字段，不改变来源或证明结果。

## 后端选择

```bash
# 默认值为 sqlite，省略选项时行为不变
python3 -m yosys_flow run --source provenance/examples/comb.v --top demo \
  --out runs/storage-sqlite --index-backend sqlite
# 整包加载的去重 gzip
python3 -m yosys_flow run --source provenance/examples/comb.v --top demo \
  --out runs/storage-gzip --index-backend gzip
python3 -m yosys_flow query runs/storage-gzip --source provenance/examples/comb.v --line 4
```

每次建档只生成选中的后端，`configuration.index_backend` 记录选择，`verified_index` 绑定具体文件。后续 `query`、`extract`、契约与 `incremental auto` 按 manifest 自动识别，不需要重复传参；原始 JSONL 始终保留。此选项用于新建归档，不会转换或覆盖已有运行目录，也没有增加常驻服务。后端选择不改变 Yosys 的综合流程。

`index_store.py` 共用去重行生成器、共享字段解码、查询视图及缓存规则。SQLite 将同一组行写入数据库并建立磁盘索引；gzip schema 3 把这些行直接写入压缩 JSON，加载时建立内存映射、位置/标签和正反向邻接索引。gzip 不先创建 SQLite，也不展开重复的大数组；旧 gzip schema 1 的整包 trace 读取兼容仍保留。两边共用来源路径、门组闭合、全部输出验证与替换条件，不能因后端变化提高关联精度。

两种新后端都在完整验证后原子发布，并绑定原始产物、版本和本机认证签名。现有索引损坏时拒绝；索引缺失、格式或实现版本变化、缺少本机密钥时按既有规则回退原始重放。gzip 与 SQLite 采用不同的签名域，不能把一种后端的签名用于另一种。

## 共享反向索引与分批维护（2026-11-10）

最终实现通过 **416 项完整回归，零失败、零跳过**，报告为 `runs/archive-scaling-final-regression/report.json`。新增验收覆盖共享集合的大规模表示、重叠来源和顺序、分批读取完整性、同名门变更拒绝、两种扫描模式下的来源/精度一致，以及流式与离线建档；既有查询、契约、导出和局部替换回归继续通过。

SQLite/gzip schema 3 将源码反查改为 `source → origin_group → object`。同一来源集合只建立一次源码到组的关联，每个最终对象或连接只登记到它所属的组，保留原有结果顺序。查询多个源码 ID 时先合并组 ID，再展开成员，避免同一大组反复读取。最终 cell 与连接分别分组；不同实例、不同来源集合、关联精度及转换边不因分组而合并。

例如 20000 个来源共同关联 20000 个门，原来会产生 4 亿对关系；现在保存 20000 项来源到组、20000 项组到门。查询全部门仍需返回 20000 个对象，压缩不能消除实际结果大小。SQLite 通过既有 `fields/items/documents` 按需读取组成员；gzip 使用完全相同的逻辑表示。旧索引实现指纹失效时回退原始证据，原捕获无需重做。

新 `run` 默认在综合期间消费已刷出的完整 JSONL 批次，维护源码 ID、对象版本、连接和转换关系的内存查询状态。生产者与消费者之间不保存一份不断增长的解析队列；未写完整的一行等待下一批。综合结束后，流式读取的 SHA-256 必须等于冻结捕获的摘要；截断、尾部多余事件、来源或版本不一致仍拒绝。完成后复用这份状态，避免再扫描、解码一遍原生日志来建立同一关系。

这是**分批维护来源图状态**；最终 SQLite/gzip 仍在 ABC 证据检查、最终来源细化、原版对照及结构匹配通过后统一写入并签名。ABC 证明尚未完成时，不提前把区域候选升级为精确关联；最终反向组、信号边界也仍在最终网表确定后建立。原始 JSONL 保留，写最终索引时仍有读取记录载荷的成本。生命周期完成后不再先整理一次粗候选、又在 ABC 证明后重做，而是只做后一次正式细化。

`YOSYS_FLOW_STREAM_REPLAY=0` 可使用离线重放作对照；`resume` 总是离线重放已有捕获。主进度文件之外，`<目录>.replay.progress.json` 报告流式处理进度，`provisional=true` 不代表归档成功。`capture_replay_overlapped` 包含等待生产者的墙钟时间，与 `traced` 重叠，不能相加；`capture_replay_drain` 是捕获绑定后等待消费者完成的额外时间。CPU 和内存会与综合器竞争，不能仅凭处理时间重叠断言总时间按同样幅度下降。

复用旧 `hyp` 捕获的完整续建档已通过：结构匹配 9.795 秒、索引构建 2044.778 秒、整命令 60 分 41 秒；SQLite 6.785 GiB，峰值 RSS 38.266 GiB，独立加载命中索引且无需重放。反向关联从潜在 1143 亿对展开改为 861816 项组成员关系。不过这份捕获的最终门共用同一个来源集合，第 239742 行仍关联整网，定位精度未因存储压缩而改善。阶段口径及证据见 [hyp 续建档结果](../../incremental/hyp-comparison.md#本轮实际结果)。

## 在线选区的大集合共享与批量证据检查（2026-11-10）

`hyp-incremental-20261110-095357` 在旧索引命中、新版前端和差分完成后，停在选区阶段，74 分 39 秒被 SIGKILL，峰值 RSS 242.388 GiB。系统有 OOM 事件，但容器无法读取内核日志，不能直接确认被杀 PID。只读抽查确认了读取缺陷：三个最终门引用数据库中同一来源文档（698017 个 ID、原始载荷 5006802 字节），却各自解码出约 24.3 MiB 的 Python 列表。原缓存排除超过 1 MiB 的载荷，选区结果又持有这些独立列表，导致磁盘去重没有转化为内存共享。

当前修复分为三层，SQLite 和 gzip 共用实现：

1. **共享数组的生命周期。** 以文档 ID 弱引用驻留共享数组；只要任一查询对象还引用该数组，其他对象就复用它，不受普通 512 项 / 8 MiB LRU 淘汰影响。无人持有且离开普通缓存后可回收，不把所有历史大数组永久缓存。共享数组拒绝直接增删修改；显式深复制仍产生独立副本，并在同一次复制内保留共享关系。
2. **按集合处理选区。** 同一来源数组与修改种子的交集只计算一次；区域及各输出的来源并集按唯一集合计算、复用。门的证据按相等来源集合分组，组内批量验证每个目标。不同组分别检查，不能因某个门从别组来源可达就判为通过。
3. **批量路径与计划写出。** 大批目标使用按事件顺序读取的边端点流，不为几十万个来源逐项查邻接、排队，也不解码不需要的证据载荷。少量目标仍采用反向查找；保留原来的时间顺序约束。反向祖先收集只保留节点集合。较大的 v2 轻量计划使用 `source_sets`，门和输出通过集合 ID 引用，避免 JSON 再次展开来源乘积；显式导出时才恢复完整说明。

`source_sets` 及每个引用均包含在计划内容哈希与重建验证中。旧的内联 v2 计划仍按原格式重建验证。来源候选精度、缺口、全部输出证明和替换条件不变。这些优化不会将 `hyp` 的整网候选改成小范围精确来源，也不代表该案例已能生成通过验收的增量网表。

索引文件结构仍为 schema 3。为了复用已有 `hyp` 归档，`index_compatibility.py` 只允许明确审查过的一对完整实现指纹；任何其他代码变化仍回退重放。原始产物/数据库哈希、原描述符 HMAC、归档绑定和本机密钥检查保持不变；不修改旧 manifest、不重新签名旧索引、不重跑插桩或建索引。兼容策略不按版本号或文件名宽泛放行。

自动流程的 `progress.json` 额外报告 `source_query`、`cell_source_paths`、`region_output_functions`、`region_supporting_evidence`、`region_plan_encoding` 等内部步骤。它们用于定位耗时，尚未完成的步骤不计为成功样本。

## 原生日志状态构造与扫描

记录器先比较实际 RTLIL cell 类型、名称、参数及标志、端口连接和 wire 名称；未变化时避免重新构造和序列化 JSON。层次实例的端口方向仍按实际模块读取。`techmap` 的信号映射在同一 pass 内复用，新增连接增量加入；替换/重写连接、移除 wire/module 及 pass 切换均使缓存失效。

## 捕获完成后的续建档

```bash
python3 -m yosys_flow resume runs/interrupted-capture \
  --out runs/resumed-archive --index-backend sqlite
```

`resume` 继承原 `run_id`、源码路径、宏、参数、层次模式和综合终点，在新的目录完成同一套验证与索引发布。原生 Yosys 只用于核对版本和二进制身份，不再执行插桩综合；仍会执行独立原版综合对照、等价检查，层次视图需要时也执行展开等价检查。`--yosys` 默认沿用原 manifest；`--native-yosys` 只允许指向哈希一致的原工具；索引后端默认继承，也可选择另一后端。

若明确要先生成索引，可在 `resume` 添加 `--skip-stock-equivalence`：只跳过原版与插桩最终网表间的结构等价检查，保留原版综合及 JSON 模块逐项一致比较、记录重放、ABC 证据、输入哈希和层次视图证明。该选项每次必须显式传入，不会从旧目录继承；正常 `run` 与不带选项的 `resume` 仍执行结构匹配检查。manifest 的 `validation_policy.stock_to_traced_equivalence` 写为 `skipped_by_request`，`validation.json` 的同名检查为 `null`，并列入 `skipped_checks`，不生成假的 `equivalence.log` 或证明耗时。

这种索引完成后可供查询、导出及区域分析使用，索引签名同时绑定跳过策略；`valid=true` 指声明策略下的记录与结构检查通过，不表示该项形式证明通过。需要原版到插桩形式证明的整网表直接复用分支仍保留原来的检查要求。加载索引和原始重放都会核对跳过标记，不能把 `null` 改成 `true` 冒充证明成功。

新 `run` 在插桩工具退出后、正式证据验证之前写出 `capture.json`，保存捕获文件哈希、输入依赖与 ABC 工具哈希、捕获起始时间及配置，并把检查点哈希写入 manifest。顶层源码还在捕获前保存摘要；包含文件和综合数据文件来自原生日志的实际 `input_files`。检查点是可恢复的输入绑定，不是证明证书。

续跑核对检查点后，以独立文件复制捕获；复制前后均检查哈希，原目录不改写、不使用硬链接。原始脚本中的旧路径保持原样，并与继承的配置逐项核对；该脚本不会再次执行。新目录不复制旧索引、旧 `validation.json` 或原版对照结果，以免把未完成工作当作通过。全部重放、证据校验、独立对照和等价检查通过后，才发布所选索引与 `status=complete`。

没有检查点的旧 v2 捕获也可尝试续跑：要求完整的 `run_end`、网表及 ABC 证据；已有输入/产物哈希会被核对，没有输入哈希时要求依赖文件和 ABC 工具的修改时间不晚于原 `traced.ys`。这种模式明确记录为 `legacy_timestamp_guard`：它不能补出当年未保存的输入哈希，也不能识别刻意回调时间戳的历史修改。源码或工具已经变化而无法确认一致时拒绝续跑，不提供跳过校验的开关。

失败或超时不授权在线增量使用。复制完成且 manifest 已绑定 `capture.json` 后，可把失败的续跑目录作为下一次输入，但必须再选一个新输出目录，重新完成验证。如果复制或检查点发布被中断，应从原始捕获目录重试，不能把该副本降级成旧版记录来接受。`timings_seconds` 记录本次执行的工作；旧时间保留在 `resume.source_timings_seconds`，缺失的旧时间保持缺失，不填成零。外层 `timeout` 控制整个续建档预算，实时阶段在目录旁的 `.progress.json` 中。

本次入口实现通过完整回归 405 项，零失败、零跳过，报告为 `runs/resume-archive-tests/regression/report.json`。随后补充复制中断保护，9 项续建档专项测试全部通过（`runs/resume-archive-tests/resume-final.log`），覆盖保留层次、展平、开发检查点、SQLite/gzip、旧记录兼容、源文件/证据损坏、证明失败及再次续跑。实际 CLI 小例子从 `cli-capture/` 续到 `cli-resumed/` 并完成源码查询；这些目录位于 `runs/resume-archive-tests/`。这证明入口功能，不代表大型 `hyp` 的后续证明或索引已经完成。

## ABC 检查点与差量

ABC 内部 schema 5 保留既有事件序号和网络快照编号，对 AIG/GIA 历史网络使用两种编码：

- `checkpoint` 保存完整节点集和输入、输出 literal。
- `delta` 引用 `base_snapshot`，保存新增/修改节点、`deleted_nodes` 及当前端口。节点内容包括操作和带极性的扇入；删除后仍被引用的节点会被拒绝。

只有同一命令、同一表示、同一 manager 的连续历史观察可以使用差量。命令/manager 切换、显式网络检查点，以及 AIG 接口压缩使缓存失效时，重新保存完整检查点；manager 销毁时清空缓存，避免地址重用串联两个网络。默认不再每 128 次观察重复写全量网络。`network_epoch` 是编码作用域；它不能证明跨快照节点身份，实际来源仍由复制、合并、映射等记录和功能验证建立。原有对象的版本、退休、复制映射和 literal 极性均保留。

重放器按序还原每个快照，检查基础快照是否为同 epoch 的最新状态、删除是否合法、端口与扇入是否完整；原先的事件计数、复制表、关系及函数校验继续执行。旧 schema 1–4 仍可读。测试专用环境变量 `YOSYS_FLOW_ABC_FULL_SNAPSHOTS=1` 可强制写完整检查点，用于比较两种编码的逐快照节点、端口和最终网表。

默认 `dc2`、`&dch` 中的 AIG 历史观察使用对象变更集合。钩子覆盖创建/回收、连接/断开、输出连接修补及扇入极性翻转；记录当前对象的实际类型和 fanin，不凭操作名称推断结果。集合保存 ID，避免对象内存回收后的悬空指针。其他命令及 GIA 仍使用扫描，首次观察和作用域切换仍保存全量。入口 NTK→AIG 转换用实际存活对象的地址索引查找 `pCopy`，保留原先的有效指针和极性规则，避免逐对象再次扫描全部 AIG。

JSONL 使用缓冲写入，在命令边界及结束时刷新并检查写入错误。异常中止可能留下未完成尾部；读取器仍要求完整的结束事件，不能将部分文件当成有效证据。

重放使用 `abc_snapshots.py` 的历史版本视图：每个 ID 保存它的值变更，快照固定版本和大小，后续新增、删除、再次使用同一 ID 都不改变旧视图。空 delta 共享节点和引用计数视图；有变化的 delta 只检查变更节点及受影响的 fanin 引用计数，不再复制整张节点字典。删除节点若仍被任何保留节点使用，会被拒绝；节点元数、端口、极性、epoch、立即前驱及复制/函数证明仍按原规则检查。所有结构检查通过后才发布新版本；完整检查点仍执行全网校验。

诊断环境变量只改变记录策略，不改变综合算法：

| 变量 | 用途 |
|---|---|
| `YOSYS_FLOW_ABC_FULL_SNAPSHOTS=1` | 每次观察写全量网络，供逐快照比较 |
| `YOSYS_FLOW_ABC_CHECKPOINT_INTERVAL=128` | 恢复周期性全量检查点；默认 `0` 仅在作用域/显式边界写全量 |
| `YOSYS_FLOW_ABC_SCAN_SNAPSHOTS=1` | 关闭 AIG 变更集合，恢复逐次扫描，用作独立对照 |
| `YOSYS_FLOW_ABC_VERIFY_DIRTY=1` | 对每次稀疏观察额外全网审计，发现漏记即报错；不用于性能测量 |

结束事件的 `capture_stats` 保存为生成快照而访问的 AIG 节点数与检查点策略；审计开关附加的验证扫描不计入这些捕获计数。这些计数不是墙钟耗时。读取器实现变更会使既有索引指纹失效，旧归档走原始证据重放，不绕过认证，也不将重建成本算作在线索引命中。

上述差量编码只压缩重复 AIG/GIA 历史网络。NTK、BLIF 仍保留原有记录方式；Yosys 原生日志另采用下述共享数组编码。完整证据解析、函数证明、非稀疏路径和索引构建仍有成本，文件减少不等于相同比例的总耗时减少，schema 5 也不表示已经补齐 `dc2/dch` 的全部因果历史。`hyp` 的旧实测与优化后手工复测命令见 [hyp 实验](../../incremental/hyp-comparison.md)；旧捕获可用 `resume` 续建档，不必重新执行插桩综合。

## 重放内存与候选集合计算

原生 JSONL 现在由 `JsonlRecords` 按行解码，常驻原始记录索引仅保存每行的 64 位文件偏移。生命周期重放仍逐条检查全部记录，保留后续来源查询需要的对象、事件和转换边；不再同时常驻一整份原始 JSON 解码树。`records` 仍支持顺序访问、下标和诊断复制；SQLite/gzip 写入的是记录内容，而不是指向外部文件的路径。扫描和读取检查文件身份及大小/时间戳，原有归档哈希和签名检查继续保留。

ABC 输入成员校验使用集合相等，去掉重复的逐节点线性列表查找。共享数组比较先判断是否为同一列表；只有不同对象才逐元素比较。这个优化不改变相等的定义，也不放过内容不一致的独立数组。

输出锥候选按同一次 ABC 调用中的输出边界集合缓存。并集使用无损位集合运算，解码后仍得到同一排序成员集合；相同候选共享成员列表和内部键。大型重叠候选中的相同成员块也共享转换边，先发布块的来源，再连接成员组和目标，保留按事件顺序查询的可达关系。边界信号到映射节点先建立查找表。细化读取重放保留的捕获事件，避免再次加载完整原始记录。精确切点仍优先采用已有证明，无法证明的仍保留候选，重跑细化时重新计算缓存，不跨证据版本复用。

`run` 向标准错误输出当前阶段，并在运行目录旁保存 `<运行目录>.progress.json`。它报告记录扫描、生命周期重放、输入/输出锥、候选细化、来源传播、ABC 证据/功能验证及索引构建；相同阶段的进度更新限流为约五秒一次。进度文件独立于归档证据，避免其持续变化破坏产物哈希。已经完成的工具阶段计时也及时保存到 manifest。外部强制终止时应结合进程是否存在及更新时间判断状态，不能仅凭残留的 `running` 判断任务还活着。

可用 `provenance/tools/replay_native.py` 对现有捕获执行有预算的诊断，不重新调用综合器。默认只验证原生记录和最终网表，`--with-abc` 才进一步验证 ABC 证据。它不写入原目录、不创建索引、不把未完成建档升级为完整归档；即使诊断通过，原版对照、全网表等价及索引发布仍是完整建档的验收条件。

## 原生来源集合与区域关系

原生 JSONL v2 通过 `shared_native_arrays_v1` feature 声明共享数组。长度至少 32 的来源 ID 和转换输入集合先写一条 `shared_array` 定义，后续事件以 `{"$native_array": id}` 引用；短数组仍直接内联。定义带独立的事件序号和当前 step ID，必须先于引用，且区分 `origins` 与 `inputs`。错用类型、未知引用、重复定义和未知来源均拒绝。记录器内的 cell/connection 及当前记录作用域共享不可变来源集合，贡献发生变化时才创建新集合。已登记集合的身份和序列化引用可直接复用，避免逐 cell 优化时反复复制、逐项比较完整来源集合。

读取端保留原始记录，解码的来源数组由对象版本和事件共享。ABC 提取成员及来源并集在 `abc_region` 验证一次，每个输出继续核对它与该区域的成员、来源和候选精度完全一致。查询图将相同的 N 个输入到 M 个输出关系表示为 `输入 → 区域节点 → 输出`；细化后的相同大成员集合也可共享节点。节点不声明新的因果证据，严格保留来源可达性、事件先后和原来的精度。不同成员集合不会因为属于同次调用而合并。

测试专用变量 `YOSYS_FLOW_NATIVE_FULL_ARRAYS=1` 可恢复内联编码，供逐项比较原始来源、最终网表和查询选择。没有该 feature 的旧 v2 日志仍可重放；旧读取器不会静默接受新编码。

## SQLite 表与按需读取

数据库在离线验证后用一个事务构建，完整性检查通过后原子发布。可检索键单独存储，载荷逐条压缩并按 SHA-256 去重。转换边的端点通过 `refs` 表归一化为整数键，事件号独立存列，剩余公共字段共享模板；不再为每条边另存整份 JSON。模板和其他载荷也以整数键引用，避免重复保存长摘要：

| 表/索引 | 用途 |
| --- | --- |
| `positions` / `source_location` | 文件及行范围查询源码身份，随后保留原有列和实例筛选 |
| `items` | 按字段与键访问对象版本、来源、连接及各类证据 |
| `edges` / `edge_from` / `edge_to` | 正反向来源关系与按原始顺序的路径检查 |
| `refs` | 源码 ID、对象版本等带类型身份与整数 SQL 键之间的映射 |
| `lookup.sources_to_final`、`lookup.sources_to_assignments` | 源码身份到最终对象及连接 |
| `lookup.drivers`、`lookup.consumers`、`lookup.aliases` | 信号的驱动、使用者和别名 |
| `tags` | 按对象、事件序号、调用及相关来源定位证据行 |
| `joint_groups` / `joint_members` | 离线追踪得到的门组最终成员、缺失成员，在线只读取触及的组 |
| `documents` | 按内容摘要去重的压缩载荷，引用使用整数主键 |
| `document_fields` | 大型来源/成员数组单独保存，各对象版本共享引用并按需还原 |

SQLite schema 3 延续之前的共享字段设计，将重复的大数组从行载荷中分离，避免对每个对象版本重新序列化、压缩和保存。同一查询中的载荷缓存仍有界；共享字段必须引用已存储的数组文档，不能递归引用自身。schema 1 索引失效时仍从原始证据重放。

表中的 `lookup.*` 是 `items.field` 值，不是另建的 SQL 表。对象反查读取对象版本中的来源 ID，再按 ID 取源码行；无需全量恢复来源表。

查询通过只读 SQLite 连接和有界载荷缓存访问这些表，不先解压整个 trace。门组闭合的成员关系在首次建档时计算，在线沿成员索引扩展触及的组，避免每次重新遍历全部 ABC 证明载荷。图遍历保留原有事件先后约束，不能把任意可达路径误当成符合日志顺序的来源链。单门只需确认路径存在时允许找到第一条后停止；契约读取成员信息时也不再为每个门生成随后丢弃的完整反查报告。自动流程的紧凑选区只返回成员与来源 ID，避免先展开完整源码详情再丢弃。目标较多时一次检查它们从所选来源出发的有序路径，不逐门重复扫描共享祖先；少量目标仍使用提前停止的反向查找。完整证据导出仍获取所需全部支持关系。

最终电气设计和少量运行上下文仍一次读入，部分显式完整诊断/导出会请求全部相关记录。每次加载仍完整计算原始产物和数据库的哈希；哈希读取采用流式实现。这些成本不会因数据库按需查询而消失。

## 认证、兼容与复核

manifest 将数据库绑定到同次运行的原始产物、运行配置及验证实现。构建前后核对原始证据；描述符通过本机密钥认证，密钥不进入归档或 Git。加载先检查文件哈希、绑定和认证，再打开数据库；修改数据库后仅重新计算普通 SHA-256 不能绕过认证。

索引缺失、实现/格式不匹配或缺少本机认证密钥时，读取原始记录重新验证，不自动修改旧归档。现有索引损坏或认证失败会拒绝；需要明确使用原始重放进行诊断。旧 gzip schema 1 仍有读取路径，新建归档默认写 SQLite，也可显式选择去重 gzip schema 3。现有旧证据不必重新综合即可重放，但新差量编码的体积收益只适用于重新记录的运行。共用存储层的实现变更会使先前索引指纹失效，旧归档此时走完整重放，不会静默改写索引。

```bash
# 建档，索引在完整验证后生成
python3 -m yosys_flow run --source provenance/examples/comb.v \
  --top demo --out runs/sqlite-demo

# 默认使用有效索引；索引失效则重放原始证据
python3 -m yosys_flow query runs/sqlite-demo \
  --source provenance/examples/comb.v --line 2

# 强制完整重放，独立于索引命中
python3 -m yosys_flow validate runs/sqlite-demo
```

## SQLite 与去重 gzip 的同数据对比（2026-10-26）

本轮先提交检查点 `f590528`，随后只增加临时实验代码，没有改动生产后端。结论是：**去重 gzip 的构建、文件体积和加载后重复查询更有优势；SQLite 的首次恢复与内存占用更有优势。现有数据不支持“SQLite 在所有阶段都更快”。**

### 固定数据与协议

使用 `runs/storage-optimization-release/{adder,bar}/baseline/base-run/` 两份已经通过验证的记录；`arbiter` 尚无验证完成的归档，因此不混入本次对比。读取原始归档时执行现有完整性与认证检查，然后只抽取一次共同的去重表示。它保留所有文档 ID、共享数组引用、转换边端点、事件顺序、查询映射和门组数据，没有减少候选证据。

这次历史微基准的共同表示是当时 schema 2 的十张逻辑表：`documents`、`document_fields`、`fields`、`items`、`refs`、`edges`、`positions`、`tags`、`joint_groups`、`joint_members`。文档保留原 JSON 载荷，公共字段继续通过 ID 引用。两边都从这一份数据生成文件：

- SQLite：按现有表结构和索引重新建库，文档逐条 zlib level 1 压缩，单事务提交，采用默认同步设置及 DELETE journal。
- gzip：将相同逻辑表保存为一个 JSON 包，文档载荷为 JSON 字符串，整体 gzip level 1 压缩；加载时建立内存字典、源码位置、标签及正反向邻接索引。它不是旧版未去重的整份 trace 序列化，也不是 gzip 压缩 SQLite 数据库。
- 两边复用同一套字段解码和生产查询/契约算法，解码文档缓存都限制为 512 项、8 MiB 原始载荷。该上限不包含 gzip 整包读取后常驻的表与内存索引，也不等于进程总内存上限。

每个电路、每个后端各三次：共 12 次构建、12 次加载与查询进程。固定随机种子 `20261026` 打乱后端/电路/重复顺序，串行运行，绑定 CPU 0；每次构建及查询均为独立进程。CPU 为 Intel Xeon Gold 5220R 2.20 GHz，Python 3.10.12，SQLite 3.37.2。

“构建”从已加载的共同去重表示开始，包含后端编码、压缩、写入、SQL 物理索引及提交；不含原始记录重放、共同归一化/去重、公共证据验证及签名。构建后的文件哈希、完整逻辑表一致性检查在计时之外，两边都执行。因此本节的 1.97 s 等数值不能直接替代前面生产流程中包含更多工作的 9.25 s 建档阶段。

“首次加载”指新进程打开后端并恢复相同的必要运行上下文。每次先校验相同原始产物，再校验本次后端文件，校验分别计时；这会预热文件缓存，**不是冷盘测试**。没有清理主机 page cache，也没有计入重新综合。

每个查询进程按 local、shared、module 顺序完成三个真实的 `source_cells` 紧凑区域计划：源码选择、有序来源路径、门组闭合、边界与全部输出函数验证、共享义务和证据引用都执行。每个任务使用新契约上下文，后端及其解码缓存持续存在；完整选区不包含新旧 RTL 差分、patch 提取或综合拼接。

之后执行五轮重复查询；每轮包含上述三个源码查询，调用真实 `query_loaded(..., compact=True)`，不使用最终查询结果缓存。重复查询不重新生成完整契约。每进程先取五轮中位数，再在三次进程结果中取中位数；下文“每批”始终指三次查询。

### 对项目的选择

本轮证实，去重和共享结构的收益并不专属于 SQLite：采用同样结构的 gzip 在这两个案例中写得更快、文件更小，加载后在内存中进行大范围或重复查询也更快。SQLite 将物理索引建设放在首次建档，在线恢复很轻，且无需在每个新进程中恢复全部表。

对于当前“每次新 RTL 启动一个进程，优先找小区域”的 CLI，继续保留 SQLite 默认后端有依据，尤其是首次响应和内存；对于数据能放入内存、长驻进程反复查询的场景，去重 gzip 值得考虑。不能用这两个案例推断所有规模的胜负，也不能将本节后端构建时间冒充全量建档时间。当前差分和函数证明瓶颈仍需独立优化，本轮没有切换生产后端。

按用户要求，该次对比的协议和结果保存后删除了 `runs/index-backend-ab/` 下的专用脚本、共同数据副本、索引副本及逐次 JSON，临时日志也已删除。既有 `storage-optimization-release` 归档、网表和回归报告保留。该次对比期间生产代码保持检查点 `f590528`；随后实现的正式双后端接口见本文开头的“后端选择”，其格式与认证检查由正式回归验收。
