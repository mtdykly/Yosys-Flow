# 来源记录与 SQLite 查询索引

首次插桩综合保存原始证据，完整验证后生成 `verified-index.sqlite3`。新版 RTL 到来后，按修改种子查询来源和转换边，重新计算本次所需区域及边界。数据库是可重建的查询副本，不替代原始证据，也不改变来源精度或替换条件。

## ABC 检查点与差量

ABC 内部 schema 5 保留既有事件序号和网络快照编号，对 AIG/GIA 历史网络使用两种编码：

- `checkpoint` 保存完整节点集和输入、输出 literal。
- `delta` 引用 `base_snapshot`，保存新增/修改节点、`deleted_nodes` 及当前端口。节点内容包括操作和带极性的扇入；删除后仍被引用的节点会被拒绝。

只有同一命令、同一表示、同一 manager 的连续历史观察可以使用差量。命令/manager 切换、显式网络检查点及每 128 次历史观察重新开始完整检查点。`network_epoch` 是编码作用域；它不能证明跨快照节点身份，实际来源仍由复制、合并、映射等记录和功能验证建立。原有对象的版本、退休、复制映射和 literal 极性均保留。

重放器按序还原每个快照，检查基础快照是否为同 epoch 的最新状态、删除是否合法、端口与扇入是否完整；原先的事件计数、复制表、关系及函数校验继续执行。旧 schema 1–4 仍可读。测试专用环境变量 `YOSYS_FLOW_ABC_FULL_SNAPSHOTS=1` 可强制写完整检查点，用于比较两种编码的逐快照节点、端口和最终网表。

上述差量编码只压缩重复 AIG/GIA 历史网络。NTK、BLIF 仍保留原有记录方式；Yosys 原生日志另采用下述共享数组编码。记录器仍扫描网络以发现变化，重放也仍要验证恢复出的状态。因此文件减少不等于相同比例的计算时间减少，schema 5 也不表示已经补齐 `dc2/dch` 的全部因果历史。

## 原生来源集合与区域关系

原生 JSONL v2 通过 `shared_native_arrays_v1` feature 声明共享数组。长度至少 32 的来源 ID 和转换输入集合先写一条 `shared_array` 定义，后续事件以 `{"$native_array": id}` 引用；短数组仍直接内联。定义带独立的事件序号和当前 step ID，必须先于引用，且区分 `origins` 与 `inputs`。错用类型、未知引用、重复定义和未知来源均拒绝。记录器内的 cell/connection 及当前记录作用域共享不可变来源集合，贡献发生变化时才创建新集合。已登记集合的身份和序列化引用可直接复用，避免逐 cell 优化时反复复制、逐项比较完整来源集合。

读取端保留原始记录，解码的来源数组由对象版本和事件共享。ABC 提取成员及来源并集在 `abc_region` 验证一次，每个输出继续核对它与该区域的成员、来源和候选精度完全一致。查询图将相同的 N 个输入到 M 个输出关系表示为 `输入 → 区域节点 → 输出`；细化后的相同大成员集合也可共享节点。节点不声明新的因果证据，严格保留来源可达性、事件先后和原来的精度。不同成员集合不会因为属于同次调用而合并。

测试专用变量 `YOSYS_FLOW_NATIVE_FULL_ARRAYS=1` 可恢复内联编码，供逐项比较原始来源、最终网表和查询选择。没有该 feature 的旧 v2 日志仍可重放；旧读取器不会静默接受新编码。

## SQLite 表与按需读取

数据库在离线验证后用一个事务构建，完整性检查通过后原子发布。可检索键单独存储，载荷逐条压缩并按 SHA-256 去重。转换边的端点通过 `refs` 表归一化为整数键，事件号独立存列，剩余公共字段共享模板；不再为每条边另存整份 JSON。模板和其他载荷也以整数键引用，避免重复保存长摘要：

| 表/索引 | 用途 |
| --- | --- |
| `positions` / `source_location` | 文件及行范围查询源码身份，随后保留原有列和实例筛选 |
| `items` | 按字段与键访问对象版本、来源、连接及各类证据 |
| `edges` / `edge_from` / `edge_to` | 正反向来源关系与按原始顺序的路径检查 |
| `refs` | 源码 ID、对象版本等带类型身份与整数 SQL 键之间的映射 |
| `lookup.sources_to_final`、`lookup.sources_to_assignments` | 源码身份到最终对象及连接 |
| `lookup.drivers`、`lookup.consumers`、`lookup.aliases` | 信号的驱动、使用者和别名 |
| `tags` | 按对象、事件序号、调用及相关来源定位证据行 |
| `joint_groups` / `joint_members` | 离线追踪得到的门组最终成员、缺失成员，在线只读取触及的组 |
| `documents` | 按内容摘要去重的压缩载荷，引用使用整数主键 |
| `document_fields` | 大型来源/成员数组单独保存，各对象版本共享引用并按需还原 |

SQLite schema 2 将重复的大数组从行载荷中分离，避免对每个对象版本重新序列化、压缩和保存。同一查询中的载荷缓存仍有界；共享字段必须引用已存储的数组文档，不能递归引用自身。schema 1 索引失效时仍从原始证据重放。

表中的 `lookup.*` 是 `items.field` 值，不是另建的 SQL 表。对象反查读取对象版本中的来源 ID，再按 ID 取源码行；无需全量恢复来源表。

查询通过只读 SQLite 连接和有界载荷缓存访问这些表，不先解压整个 trace。门组闭合的成员关系在首次建档时计算，在线沿成员索引扩展触及的组，避免每次重新遍历全部 ABC 证明载荷。图遍历保留原有事件先后约束，不能把任意可达路径误当成符合日志顺序的来源链。单门只需确认路径存在时允许找到第一条后停止；契约读取成员信息时也不再为每个门生成随后丢弃的完整反查报告。自动流程的紧凑选区只返回成员与来源 ID，避免先展开完整源码详情再丢弃。目标较多时一次检查它们从所选来源出发的有序路径，不逐门重复扫描共享祖先；少量目标仍使用提前停止的反向查找。完整证据导出仍获取所需全部支持关系。

最终电气设计和少量运行上下文仍一次读入，部分显式完整诊断/导出会请求全部相关记录。每次加载仍完整计算原始产物和数据库的哈希；哈希读取采用流式实现。这些成本不会因数据库按需查询而消失。

## 认证、兼容与复核

manifest 将数据库绑定到同次运行的原始产物、运行配置及验证实现。构建前后核对原始证据；描述符通过本机密钥认证，密钥不进入归档或 Git。加载先检查文件哈希、绑定和认证，再打开数据库；修改数据库后仅重新计算普通 SHA-256 不能绕过认证。

数据库缺失、实现/格式不匹配或缺少本机认证密钥时，读取原始记录重新验证，不自动修改旧归档。现有数据库损坏或认证失败会拒绝；需要明确使用原始重放进行诊断。旧 `verified-index.json.gz` 仍有读取路径，新建归档只写 SQLite。现有旧证据不必重新综合即可重放，但新差量编码的体积收益只适用于重新记录的运行。

```bash
# 建档，索引在完整验证后生成
python3 -m yosys_flow run --source provenance/examples/comb.v \
  --top demo --out runs/sqlite-demo

# 默认使用有效索引；索引失效则重放原始证据
python3 -m yosys_flow query runs/sqlite-demo \
  --source provenance/examples/comb.v --line 2

# 强制完整重放，独立于索引命中
python3 -m yosys_flow validate runs/sqlite-demo
```

## 验收与计时

`test_abc_delta.py` 比较真实 ABC 两种编码恢复出的每个网络与最终网表，并测试删除、极性、错误基础快照和悬空引用。`test_sqlite_index.py` 将索引查询与原始重放逐字段比较，覆盖保留层次、展平、开发检查点、文件损坏、认证、回退、SQL 查询计划及禁止完整历史遍历的点查询。随机图测试检查索引遍历与原始按序扫描的一致性。

最终实现的完整回归为 **352 项通过，零失败、零跳过**，报告在 `runs/storage-optimization-release-regression/report.json`。新增检查包括原生共享数组与内联编码一致性、共享引用损坏、紧凑选区路径、128 位转义标量加法器、32 位桶形移位独立函数。这是项目回归数量，不是 EPFL 案例数量。早期回归的一项旧 mock 参数适配错误及其专项复测仍保留在 `runs/storage-optimization-regression/`；最终完整回归已经重新执行，未覆盖早期报告。另一次包含译码控制排序试验的 353 项回归也保留；该排序因 EPFL 建档退化，连同其专用测试从默认实现撤回。

最终单次 EPFL 复测见 `runs/storage-optimization-release/report.json`：`adder/bar` 建档分别约 60.83/89.34 s、77.21/209.22 MiB；`adder_local` 首次通过细粒度局部综合、拼接与全部输出验证，生成耗时 6.75 s。`adder_shared` 仍缺少来源证明，`bar` 仍缺少函数及来源证明；`arbiter` 的插桩综合已完成，但完整建档在记录验证阶段达到 360 s 上限。体积改善并未消除所有计算或证据缺口；前后口径和未成功项均保留在下述规模实验文档。

前一存储检查点 `c94b7a7` 的完整回归为 346 项通过，零失败、零跳过；报告保存在 `runs/comparison-anubis-functional-v4/sqlite-release-regression/report.json`。这是项目回归数量，不是 EPFL 案例数量。180 s / 1 GiB 预算下的 EPFL 复测有 36 个预定样本：18 次全量成功、6 次增量超时、12 项因旧归档不可用未启动。

同一实现进一步使用 360 s / 8 GiB 预算复测：`adder` 建档 80.000 s，`bar` 建档 342.784 s，两者均成功；`arbiter` 在 190.724 s 触发体积保护。36 项中，18 次全量成功、6 次 `adder` 增量因区域证据不足拒绝替换、6 次 `bar` 增量超时、6 项 `arbiter` 增量未启动。另把 `arbiter` 的体积限额提高到 32 GiB，仍在 360 s 超时，停在插桩综合的 ABC 后优化阶段，尚未进入记录验证。这些结果仍未产生有效的增量加速比。

实测分别报告原始记录/数据库/整份归档字节数、插桩工具耗时、重放验证耗时、建索引耗时以及在线哈希、加载与选区耗时。`incremental auto` 的 `progress.json` 保存已完成阶段和当前阶段，即使外层保护终止进程也可定位最后进度；未完成阶段不能冒充成功计时。EPFL 的固定案例、预算和前后对比见[规模实验](../../incremental/epfl-comparison.md)。1 GiB 是首轮实验设置的产物保护，并非格式容量上限；后续实验分别采用 8 GiB 和 32 GiB，数据库及其他产物都计入总量。上述预算通过实验命令传入，没有修改工具的全局默认值。
